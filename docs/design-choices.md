# 关键方案说明（为什么这样设计）

> 原则：直接采用正确方案；每项写清「为什么 / 好处 / 解决什么问题」。  
> 不采用「先给错误方案再纠正」的教学路径。

---

## 1. 语料：公司内部文档风（中文为主）+ 多格式

**方案**：虚构「星云科技」内部制度/FAQ/SOP（MD）+ Wiki（HTML）+ 通讯录（CSV）。

| | |
|--|--|
| **为什么** | 国内落地多数是中文内部知识库，不是英文开源文档站 |
| **好处** | 提问方式、术语、审批口径都贴近真实场景；中英混排（系统名/缩写）也会自然出现 |
| **解决什么** | 避免「只会检索英文技术文档」却不会做企业知识库的错位 |

---

## 2. 建库与问答分离（`--ingest` / `--query`）

**方案**：入库单独跑；提问只走检索 + 生成。

| | |
|--|--|
| **为什么** | 入库要对全库做 embedding，贵且慢；提问应是毫秒～秒级体验 |
| **好处** | 成本可控、延迟可控；语料不变时不必重复嵌向量 |
| **解决什么** | 避免「每问一次就重嵌整库」的浪费与卡顿 |

## 2.1 统一知识库（用户不选库）

**方案**：`data/corpus/<名>/` 只是整理文件的文件夹；`ingest` 全部入库到同一个向量库；用户 `--query` 自动查全部。

| | |
|--|--|
| **为什么** | 智能客服场景下，终端用户不应、也不会知道「去哪个库查」 |
| **好处** | 产品体验正常；新增制度/FAQ 只需丢文件再 ingest |
| **解决什么** | 把「运维怎么组织目录」误做成「用户要选库」 |

---

## 3. 分块：按 Markdown 标题切分

**方案**：`chunk_by_heading`——一节（标题+正文）一块；单节过长再按段落打包。

| | |
|--|--|
| **为什么** | 制度/FAQ 本身按章节组织，检索单位应与阅读单位一致 |
| **好处** | 条款带着所属标题；命中「年假」时不会和「迟到补卡」糊在同一块里 |
| **解决什么** | 固定字数硬切导致的：切断条款、丢失章节语境、检索分数被噪声稀释 |

---

## 4. Embedding：`check_embedding_ctx_length=False`

**方案**：对国内 OpenAI 兼容网关直接传字符串列表。

| | |
|--|--|
| **为什么** | LangChain 默认按 OpenAI/tiktoken 预处理，和部分 MaaS embedding 协议不兼容 |
| **好处** | 调用稳定；向量仍由同一 embedding 模型计算 |
| **解决什么** | `contents is neither str nor list of str` 一类 400 错误 |

（超长文本靠上游分块控制，而不是依赖错误的 OpenAI tokenizer 切分。）

---

## 5. 生成：强制引用 + 无依据拒答

**方案**：系统提示词要求只根据上下文作答，并标注 `[1][2]…`。

| | |
|--|--|
| **为什么** | 内部制度场景，胡编比「答不上来」危害更大 |
| **好处** | 答案可追溯；便于区分「检索错了」还是「模型瞎写」 |
| **解决什么** | 自信幻觉、无法审计、员工按错误制度执行 |

---

## 6. LLM：区分可重试错误 + 退避 + 强弱降级

**方案**：限流/超时/5xx 才重试；鉴权/参数错误不重试；强模型仍失败则降级便宜模型。

| | |
|--|--|
| **为什么** | LLM 失败形态和普通 API 不同；盲目重试既费钱又拖慢 |
| **好处** | 瞬时故障可恢复；永久错误快速失败；可用性更高 |
| **解决什么** | 限流导致整页挂死、参数错误空转烧额度 |

---

## 7. 后续会直接采用的增强（需要时再加，仍是正确方案）

| 方案 | 为什么 / 解决什么 |
|------|------------------|
| 混合检索（向量 + BM25） | 工号、专有名词、精确制度编号等关键词场景，纯向量容易漂 |
| 重排（cross-encoder） | top-k 里常有「语义沾边但不相关」的块，重排提升精排质量 |
| Langfuse 追踪 | 看见每次检索到的 chunk、耗时与成本，才能高效排查 |
| Eval / golden set | 用数字验证改动，避免「感觉变好了」 |

加这些时同样会先讲清理由，再改代码——不会先上一个明知更差的版本。

---

## 8. 检索增强：过滤 + 子查询分解 + 父文档扩展

**方案**：三项能力做成可插拔模块（`RetrievalOptions`），默认全关，与 Week 6 baseline 一致。

| 能力 | 实现 | 日后归属 |
|------|------|----------|
| **过滤** | 重排后按 `RETRIEVAL_MIN_SCORE` 丢低分 chunk；`metadata_filter` 按 domain/kind/corpus 预演分库 | COMMON_PROFILE（阈值各 KB 可覆盖） |
| **子查询分解** | cheap LLM 拆复合问句 → 多路检索 → RRF 合并 | COMMON_PROFILE（通讯录等单主题 KB 可关） |
| **父文档扩展** | 切块时存 `parent_text`；命中子块时扩展为整节 | COMMON_PROFILE（短块 KB 可关） |

| | |
|--|--|
| **为什么** | 第 8 周要拆多 KB + Profile，需先把「可配置检索层」做出来并在单库验证 |
| **好处** | 开关独立、eval 可五路对照；入库元数据（domain/corpus/parent）为分库过滤铺路 |
| **解决什么** | 复合问只检一次漏半边；子块上下文不足；候选里混低相关噪音 |

**验收**：`uv run python tests/eval/compare.py --suite enhanced`；父文档扩展需先 `--ingest --reset`。
